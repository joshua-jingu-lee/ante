# D-020: 도구 중립 개발·기여 원칙 (2026-08-22)

> Ante 설계 결정 기록.
> 인덱스: [README.md](README.md)
> 상태: **확정**
> 관계: D-019에서 특정 Claude Code 절차를 공통 필수 경로로 둔 부분과 외부 이슈 제보 전제를 대체한다. `source:ante-oracle` 등 내부 생성 미검증 이슈의 검증은 유지한다.

**결정**: Ante의 개발·기여 수용 기준은 저장소의 스펙과 기여 규칙, 공개된 검증 명령, CI 결과와 유지관리자의 판단으로 정한다. 특정 AI 모델, CLI, 플러그인이나 명령을 필수로 요구하지 않는다. AI 도구별 자동화는 이 기준을 돕는 선택 사항이며 공통 수용 기준을 바꿀 수 없다.

**운영 원칙**:

- Ante는 단독 유지관리자 주도 프로젝트다. 범위, 설계, 병합과 릴리스는 유지관리자가 최종 결정하며, PR의 응답·검토·병합 여부나 시점을 보장하지 않는다.
- GitHub Issues는 유지관리자와 권한을 부여받은 협업자의 공개 작업 목록으로 사용하고, 새 이슈 생성 정책은 [`Collaborators only`](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/disabling-issues)로 둔다.
- 내부 작업은 기존 이슈 우선 절차를 따른다. 협업자가 아닌 외부 기여자의 변경은 PR로만 받으며, 선행 이슈를 요구하지 않는다. PR 자체를 제안·논의·검증 기록으로 사용하고, 후속 작업이나 범위 분리가 필요할 때만 유지관리자가 이슈를 만든다.
- 공개 기여 절차와 필수 검사의 정본은 `CONTRIBUTING.md`로 두고, `README.md`, `AGENTS.md`와 런북은 이를 참조한다.
- 코드 변경 없는 기능 제안, 일반 지원 요청과 패치 없는 일반 버그 신고를 위한 별도 창구는 운영하지 않으며 GitHub Discussions도 활성화하지 않는다. 보안 취약점은 아래의 비공개 신고 경계를 따른다.
- 외부 PR은 변경 목적과 범위, 수행한 검증을 설명해야 한다. 변경이 현재 스펙의 공개 계약을 바꾸면 관련 스펙도 함께 수정한다.
- 기본 브랜치에 직접 푸시하지 않고 브랜치와 PR을 사용한다. 공개된 필수 검사를 통과한 뒤 유지관리자가 병합한다. 내부 AI 자동화의 계획·리뷰 절차를 외부 기여자에게 요구하지 않는다.
- 기여가 사람이나 AI 중 누구에게서 왔고 어떤 도구로 작성되었는지는 평가 기준이 아니다. 제출자는 변경의 정확성, 라이선스와 보안을 책임진다.

**외부 PR 안전 경계**:

- 유지관리자가 승인하지 않은 PR 코드는 저장소 위치와 관계없이 신뢰하지 않는다.
- 병합 전 외부 PR 검증은 시크릿이 없고 읽기 전용인 GitHub 호스팅 CI에서만 실행한다. 홈서버나 자체 호스팅 러너에서는 PR 코드를 실행하지 않는다. 쓰기 권한이 있는 워크플로는 PR 코드를 체크아웃하거나 실행하지 않으며, 권한 작업은 유지관리자가 확인한 정확한 커밋 SHA만 대상으로 한다.
- 실제 거래 계정, 자격증명과 개인 거래 데이터는 저장소, 이슈, PR, 로그나 공개 CI에 넣지 않는다.
- 취약점은 `SECURITY.md`에 안내한 [비공개 취약점 신고](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/report-privately) 경로로 받으며 공개 이슈나 PR에 세부정보를 남기지 않는다.

**근거**:

- 단일 AI 도구의 장애, 사용량이나 기능 변경이 필수 개발 경로를 막아서는 안 된다.
- 공개 이슈와 지원 창구를 누구에게나 열면 단독 유지관리자가 감당해야 할 분류 작업이 늘어난다. 코드와 검증 근거를 담은 PR만 외부 입력으로 받는 편이 현재 운영 여력에 맞다.
- 외부 PR 자체가 공개 작업 기록이므로 수용을 위해 같은 내용을 이슈로 다시 만들 필요가 없다.
- Ante는 홈서버에서 실제 자금과 자격증명을 다루므로 외부 코드와 권한 있는 실행 환경을 분리해야 한다.

**검토한 대안**:

- **특정 AI 도구의 계획·리뷰 절차를 계속 필수화**: 도구 장애가 전체 개발을 막고 외부 기여자가 같은 절차를 재현할 수 없어 채택하지 않는다.
- **외부 Issues나 Discussions 운영**: 분류·지원 부담이 현재 유지관리 여력을 넘으므로 채택하지 않는다.
- **여러 AI 도구를 통합하는 자체 프레임워크 구축**: 실제 반복 수요와 유지비 절감이 확인되지 않았으므로 채택하지 않는다.

**영향과 이행**:

- D-019의 내부 계획·리뷰 자동화와 `source:ante-oracle` 등 내부 생성 미검증 이슈의 검증은 선택적으로 유지한다. 특정 Claude Code 명령의 성공을 모든 PR의 공통 필수 조건으로 삼거나 외부 이슈 제보를 전제하는 부분은 이 결정이 대체한다.
- 공개 진입점은 기존 `README.md`, 한 페이지의 `CONTRIBUTING.md`와 짧은 `SECURITY.md`로 제한한다. 지원 미운영과 유지관리자의 최종 결정권은 `CONTRIBUTING.md`에 함께 적는다.
- `AGENTS.md`와 런북은 내부 이슈 우선 경로와 외부 PR 경로를 구분하고, AI 도구별 절차가 선택 사항임을 밝히는 데 필요한 부분만 고친다.
- GitHub에서는 Issues를 `Collaborators only`로 두고 Discussions를 비활성화하며 비공개 취약점 신고를 활성화한다.
- 이행은 공개 문서 정리, GitHub 설정 반영, 외부 포크 PR의 시크릿 없는 CI 확인 순서로 수행한다.
- 이 정책은 패치를 작성할 수 없는 사용자의 제안과 일반 버그 신고를 놓칠 수 있다는 비용을 감수한다. 실제 수요나 공동 유지관리자가 생기면 그때 지원 창구와 거버넌스 체계를 다시 검토한다.
